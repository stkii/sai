# HUMANS.md

このファイルは、**AI から人間へのお願い**です。
SAI の開発で私（Claude Code）がうまく働けるかどうかは、指示の出し方と、私が確認できない情報をもらえるかどうかでかなり変わります。ここには、その具体的な内容を書いています。

守ってもらえないと動かない、という類のものではありません。ただ、ここに書いたことが満たされているときと、そうでないときで、私が出す成果物の質はかなり変わります。

## 1. 指示を出すとき

### どのレイヤーの話かを教えてください

分析の計算は `src-r/`、入力 UI と結果表示は `src/`、R との受け渡しは `src-tauri/` が担当します（[docs/ARCHITECTURE.md](./ARCHITECTURE.md)）。

そのため「記述統計を直して」とだけ言われると、私は**どの層の話なのか推測する**ことになります。推測が外れると、症状が出ている層だけを直して、原因は残ったままになります。

- どのレイヤーの話か（`src/` / `src-tauri/` / `src-r/`）
- 計算結果の話なのか、画面（入力 UI・表示）の話なのか

このどちらかがあれば十分です。計算結果の誤りは、Rust が配管に徹している設計なので、原則 `src-r/` を直します。

### 「いい感じに」だけだと結果がぶれます

このプロジェクトには互いに衝突しうる方針が複数あります。

- SPSS と一致させる（統計出力のポリシー）
- 暗黙の変換をしない（ダークパターンの禁止）
- YAGNI（先回りして作らない）
- レイヤーの依存方向を守る（`docs/ARCHITECTURE.md`）

普段は衝突しませんが、衝突する場面では私が勝手に優先順位を決めてしまいます。「ここは通知より互換性を優先して」のように、一言もらえると手戻りが減ります。

### 恒久的なルールは会話ではなく `CLAUDE.md` に書いてください

会話の中で言われたことは、その会話の中でしか効きません。長い作業では前半のやり取りが要約されるため、取りこぼす可能性もあります。「今後ずっとこうしてほしい」という内容は、会話で言うだけでなく `CLAUDE.md` に書いてもらえると確実です。

### 方針が変わったら、変わったと言ってください

前の指示を取り消したのか、追加したのかが分からないと、私は両方を同時に満たそうとして中途半端なものを作ります。「さっきの話はナシで」の一言で十分です。

## 2. 統計の値について

### SPSS の値は私が出せません

分析結果は、可能な限り SPSS と一致させる方針です。ただし**私は SPSS を実行できません**。R を動かして `lm` や `cor.test` の出力と一致することは確認できますが、それは「SPSS と一致している」ことの証明にはなりません。

`src-r/tests/testthat/` に入れる期待値のうち、SPSS 固有の値（`psych::describe(type = 2)` の歪度・尖度、`EFAtools::EFA(type = "SPSS")` の因子分析など）は、出典が必要です。

- SPSS の実際の出力をもらえるのが最良です
- 無理な場合は、どの教科書・論文・データセットの値かを教えてください

出典なしで期待値を私に作らせると、「実装が出した値をそのまま期待値にする」ことになり、テストが実装のコピーになって意味を失います。この状態は外から見て気付きにくいので、特に避けたいところです。

### SPSS と合わない・合わせられないとき

期待値と実装が合わないとき、許容誤差を広げる・丸め方を変える・条件を足すといった操作をすれば、テストは簡単に通ります。ただしそれは統計的な正しさとは無関係なので、原則として私からは提案だけして、判断は仰ぎます。私が黙ってこれをやっていたら、それは私のミスなので指摘してください。

SPSS と一致させられない場合は、無理に寄せずに、理由と SPSS との違いを記録する方針です。記録先は、その都度相談させてください。「合わない」と分かった時点で、その旨を伝えてもらえれば記録します。

## 3. 私が確認できないこと

私が「できた」と言えるのは、基本的にビルドが通ってテストが緑になったところまでです。次のことは私の側では確認できません。

- **画面の見た目と操作感** — GUI を起動しての目視確認は、人間が見た方が確実で速いです
- **実データでの挙動** — 手元の実データや、研究で実際に使う CSV / SAV での結果
- **macOS 以外の環境** — 動作確認は macOS のみという前提です
- **R 環境の実体** — `renv` のプロファイル、インストール済みパッケージの版
- **配布版の別マシンでの動作** — 同梱した R パッケージは、ビルド時と同じ R の版・CPU・OS を前提にしています（[docs/DEVELOPING.md](./DEVELOPING.md)）。移動後の同梱 R を使うテストは走らせられますが、R が入っていない・版が違うマシンでの挙動は確認できません

「テストは通った、画面は未確認」という状態のときは、私はそう書きます。逆にこれを書いていないのに確認できていない場合は、報告の仕方が雑になっているので指摘してください。

## 4. ドキュメントの鮮度

私は作業を始めるとき、`CLAUDE.md` と `docs/` を読んで前提を組み立てます。ここが実装と食い違っていると、**間違った前提のまま一貫して間違ったコードを書きます**。しかも自信を持って書くので、見た目では気付きにくくなります。

- 実装を変えたときは、対応する文書も更新する指示を一緒に出してもらえると助かります
- `docs/ARCHITECTURE.md` が掲げている「設計書は実装の影」というスタンスは、私にとって実利があります
- `CLAUDE.md` と `HUMANS.md` は内容が対応しています。片方を変えたらもう片方も更新してください

また、`docs/TODO.md` の「見送ったもの」の記録はとても助かっています。理由まで書いてあるので、私が同じ提案を蒸し返さずに済みます。

## 5. うまくいった伝え方

これまでの作業で、特に効いたものです。

- **エラーは全文貼ってください** — 要約されると原因の特定に往復が増えます。逆にファイルの内容は貼らずパスで十分です（自分で読みます）
- **「なぜそうしたいのか」が一行あると精度が上がります** — 手段だけ指定されるとその通りに作りますが、目的が分かれば前提の誤りに気付けることがあります
- **既存の似た実装を教えてください** — 「`descriptive` と同じ形で」のような指定は、命名も構造も揃うので確実です
- **否定形より肯定形** — 「〜しないで」だけだと代わりに何をすべきかが分からず、別の外し方をすることがあります

## 6. 私を疑ってほしいところ

最後に、私が間違えやすい場所です。レビューするならここを優先してください。

- **統計の値そのもの** — コードの形が正しくても、式や推定量の選択を間違えることがあります
- **エッジケース** — 欠損値、全て同一の値、n が極端に小さい場合の扱い
- **「暗黙の変換をしない」の抜け** — 通知のつもりで書いた箇所が、実際にはユーザーに届いていないことがあります
- **R と Frontend の二重定義** — メソッド一覧は Frontend の `ANALYSIS_METHODS` と R の dispatch table（`cli.R`）が別々に持っています。片方にだけ追加して、もう片方を忘れていないか
- **コメントの中身** — 規約では、残してよいのは自明でない WHY だけです。何をしているかの説明や、経緯の説明が混ざっていないか

私が書いたコードだからといって、他より信用する理由はありません。おかしいと思ったところは、遠慮なく聞いてください。
