# 数値計算とエラー処理の方針

## この文書について

`src-cpp/` のすべての統計手法と変数変換が従う、エラーの伝え方、浮動小数点の扱い、許容誤差、SPSSとの一致の基準を定めます。手法ごとの計算式や返す値は [手法別の仕様](methods/) に書き、この文書には書きません。

全体の構成方針は [C++統計分析エンジンの構成方針](ARCHITECTURE.md)、作業手順は [記述統計までの実施ステップ](../../CPP_MIGRATION_STEPS.md) を参照してください。

新しい手法を追加するときは、この文書の基準で例外・診断・許容誤差・メッセージを判断します。基準では判断できない事例に出会った場合は、その手法を実装するより先にこの文書を更新します。

## エラーの伝え方

### 3つの区分

| 区分 | 何が起きたか | 伝え方 | 例 |
| --- | --- | --- | --- |
| 契約違反 | 公開APIの前提条件が満たされていない。呼び出し元のコードを直せば消える | 例外 | 値と欠損マスクの長さが違う。マスクが0でも1でもない。欠損でない行に NaN がある。尺度の下限が上限以上 |
| 統計上の未定義 | 入力は契約を満たすが、その手法の定義上その統計量が存在しない | 診断と、値を返さないこと | 有効件数が3件で歪度を求められない。分散が0で標準化できない |
| 数値表現の限界 | 定義上は存在するが double では表せない | 診断と、値を返さないこと | 標準偏差が double の範囲を超える。平均が有限でなくなる |

判断の順番は「呼び出し元がコードを直せばこの状態は消えるか」です。消えるなら例外、消えないなら診断です。

利用者のデータがそうであることを理由に例外を投げません。空の列、全欠損の列、定数列、件数が足りない列は、いずれも正常な入力です。

削除した実装は、平均が有限でなくなった場合を `std::overflow_error` にしていました。本方針ではこれを「数値表現の限界」として診断へ移します。入力がすべて有限で契約を満たしているなら、呼び出し元に直せる誤りはなく、利用者が読める形で伝えるべき事象だからです。

### 例外

自分から投げる例外は `std::invalid_argument` だけを使います。例外は利用者向けの表示文言の供給源ではなく、開発者とログに向けた通知なので、細かい型の分類を必要としません。細分が必要な事例が出た場合は、型と使い分けをこの文書に追記してから使います。

`std::bad_alloc` や `.at()` の `std::out_of_range` など、標準ライブラリが投げるものはそのまま伝播させます。握りつぶしません。

例外はC互換境界を越えません。`adapters/c_api/` の関数は `noexcept` とし、内部ですべての例外を捕捉してエラーコードとメッセージへ変換します。

`noexcept` は、投げないことを保証できる関数にだけ付けます。入力検証を行う公開API関数には付けません。付けると契約違反が `std::terminate` になり、呼び出し元がメッセージを受け取れなくなります。

### 診断

診断は、コードと対象と件数を持つ構造化データです。表示文を持ちません。共通の型は `include/sai/core/diagnostic.hpp` に定義します。

- 手法ごとに独立した列挙型を作らず、共通のコードに寄せます。手法が増えたときに、RustとGUIの両方で全対応を書く事態を避けるためです
- 重大度のフィールドは設けません。現時点の診断はすべて「要求した値が返らなかった理由」か「対象件数の説明」で、区別が必要になった実例がありません。必要になった時点で追加します
- 「どの値が返らなかったか」は、`"standard_deviation"` のような安定した文字列キーで持ちます。統計量ごとの列挙型を作ると、手法が増えるたびにRustとGUIの両方へ分岐が増えるためです。キーはsnake_caseとし、結果構造体のフィールド名と一致させます。静的な文字列リテラルなので、C境界では所有権を持たないポインターと長さで渡せます
- 未定義の値は `std::optional` の空で表します。0、NaN、空文字列で代用しません
- 診断が空であることは「要求したすべての値が返った」ことを意味します。この対応を崩す診断を追加しません
- オプションで無効にした統計量について診断を出しません。利用者が選ばなかったことは異常ではありません

診断コードの意味を変えるとき、または削除するときは、GUIの表示文言の更新を同じ変更に含めます。

### メッセージ

文言は英語で書きます。利用者が読む日本語は、診断コードと対象からGUI側が組み立てます。C++側に表示言語を持ち込みません。

- 1文で書き、平叙文にして、末尾にピリオドを置きます
- `[ERROR]:` のような接頭辞を付けません。例外の型と発生箇所が分類を担います
- 満たされなかった条件、実際の値、位置の3つを必ず含めます
- 位置は、列を特定できる識別子と、1始まりの行番号で示します。行に紐づかない契約違反では、対象の識別子と、満たされなかった値の組を示します
- 呼び出し元が列名を渡さなかった場合は `the column` と書きます。名前がないことを理由にメッセージを省きません
- 利用者と開発者が目にする行番号は1始まりです。内部の添字は0始まりのまま扱い、メッセージへ出す直前に1を足します
- 数値は `{:.17g}` で出します。丸めた値を出すと、原因になった値を判別できません

```text
The values and the missing mask of column "age" differ in length: 150 and 149.
Row 7 of column "age" has a missing mask value of 2; each element must be 0 or 1.
Row 42 of column "age" holds inf; rows not marked missing must hold a finite value.
```

この3つは `src/core/data_view.cpp` が実際に出す文字列で、`tests/unit/data_view_test.cpp` が全文一致で照合します。文言を変えるとテストが落ちるため、この例と実装がずれることはありません。

メッセージの組み立てには `std::format` を使い、1箇所のヘルパーへ集約します。書式を全手法で揃えるためと、標準ライブラリの対応状況が環境によって違ったときに1箇所で対処するためです。

## 浮動小数点の扱い

実数は `double` を使います。

### ビルドが強制する規則

次は違反するとビルドかCIが落ちます。守られているかを人が確かめる必要はないので、根拠だけ残します。

| 規則 | 強制手段 |
| --- | --- |
| `==`・`!=` で浮動小数点を比較しない | `-Wfloat-equal` |
| `float` を計算と公開APIに持ち込まない | `-Wdouble-promotion` |
| C-style cast を使わない | `-Wold-style-cast` |
| `NULL` や `0` ではなく `nullptr` を使う | `-Wzero-as-null-pointer-constant` |
| オーバーライドに `override` を付ける | `-Wsuggest-override` |
| `-ffast-math`・`-Ofast`・`/fp:fast` を使わない | CMakeがconfigureで `FATAL_ERROR` |
| `using namespace std` を使わない | CIの検査 |
| C標準ライブラリのヘッダーを含めない | CIの検査 |

fast-mathだけは理由が数値計算固有です。NaNと無限大が存在しない前提を置き、演算の結合順序の入れ替えを許すため、この文書が定める有限性の判定と総和の順序がどちらも無効になります。設定は好みではなく誤りなので、警告ではなくビルドの停止にしています。

ビット単位の同一性そのものを意図する比較（入力を変更していないことの確認など）だけは例外です。理由をコメントに書いたうえで、その箇所で `-Wfloat-equal` を局所的に抑制します。

### 人が守る規則

- `long double` を使いません。精度がプラットフォームによって異なり、保存済み参照値との比較が環境依存になります
- 有限性は `std::isfinite` で判定します。`x != x` のような書き方をしません
- 閾値と定数は名前付き定数にします。定数の近くに出典を書き、SPSS資料に基づく値か、SAIの採用仕様かを区別します
- 0除算はコードで防ぎます。分母が0になりうる箇所は、件数や分散の条件で事前に排除してから割ります

### 集計

- 総和や平方和を単純な加算で積み上げません。逐次更新を使い、桁落ちを避けます
- オーバーフローを避けるための中心化とスケーリングは許可します。ただし、その変換が統計量の定義を変えないこと（尺度不変な量に限るか、最後に元の尺度へ戻すこと）を関数のコメントで示します。閾値の判定は元の尺度で行います
- 入力列を並べ替えません。順序が必要な計算は作業用のコピーに対して行います

これらは、結果を利用者に断りなく変える処理ではありません。同じ定義の値を、より狭い誤差で求めるための手段です。

## 許容誤差

### 既定

比較式は次のとおりです。

```math
|\mathrm{actual} - \mathrm{expected}| \le \mathrm{abs\_tol} + \mathrm{rel\_tol} \times |\mathrm{expected}|
```

| 対象 | 既定 |
| --- | --- |
| 絶対誤差 `abs_tol` | `1e-12` |
| 相対誤差 `rel_tol` | `1e-10` |
| 件数・行数・列数などの整数 | 完全一致 |
| 診断コードの集合 | 完全一致 |

現行の `tests/fixtures/descriptive/` に記録されている値と同じです。

GoogleTest の `EXPECT_NEAR` は絶対誤差だけを見るため、この式を満たす比較ヘルパー `tests/support/tolerance.hpp` の `sai::test::is_near` を全手法で共有します。

### 手法ごとの上書き

手法ごとに緩めてかまいません。条件は、値と理由をその手法の `docs/methods/` と該当する fixture の両方に書くことです。片方だけの記載は認めません。厳しくする場合も同様に記録します。

書いてよい理由は、たとえば次のようなものです。反復計算の収束判定が参照ソフトと異なる。参照値として得られる桁数が足りない。条件数の大きい行列を含む。

「実装が通らないから」は理由になりません。

### 期待値を動かさない

テストを通す目的で、保存済みの期待値を書き換えません。差が出た場合は原因を調べ、実装の誤りか、参照側の計算条件の違いか、許容誤差の設定かを区別してから直します。参照値を再生成したときは数値差を確認し、生成環境を記録します。

## 「SPSS準拠」の定義

手法ごとに、次の3段階のどれに当たるかを `docs/methods/` の冒頭に書きます。段階が上がったら書き換えます。

| 段階 | 意味 | 残す根拠 |
| --- | --- | --- |
| A：実機照合済み | SPSS本体を実行し、出力と照合した | `validation/spss/` のシンタックスと実行条件、SPSSのバージョン |
| B：式一致 | SPSSのアルゴリズム文書の式と実装が一致し、参照値はRで生成した | 文書のページ番号と、R側で指定したオプション |
| C：SAI採用仕様 | SPSSに対応する仕様がない、または意図的に変えた | 採用理由と、SPSSとの差異 |

「SPSS準拠」と書けるのはAとBだけです。CをAやBと混ぜて書きません。1つの手法の中で統計量ごとに段階が違ってかまいません。たとえば記述統計では、平均・標準偏差・歪度・尖度がB、中央値はDESCRIPTIVES章に載らないためCになります。

### BとしてRの参照値で代用してよい条件

次をすべて満たす場合に限ります。

- SPSSのアルゴリズム文書に計算式が明示されていて、ページを引用できる
- 反復計算、収束判定、並べ替えの任意性を含まない
- Rのオプションでその式に一致させられ、どのオプションを使ったかを記録できる
- 参照値の生成環境（Rとパッケージのバージョン）を fixture に記録する

fixture には「これはRの参照値であり、SPSS本体の出力ではない」ことを書き続けます。

### Aとして実機照合が必要な条件

次のどれかに当てはまる手法は、R由来の参照値だけで「SPSS準拠」と書けません。

- 文書に式がない、または既定値が文書化されていない
- 反復計算と収束判定を含む（因子抽出、多次元尺度構成法、最尤推定）
- 回転、符号の向き、成分の並び順の規約が結果に出る
- タイ、境界、パーセンタイルの補間規則が結果に出る
- 欠損処理の適用順序によって結果が変わる

該当する手法は、実機照合を終えるまで段階Cとして扱い、未照合であることを仕様に明記します。

### Rを正解として扱わない

RとSPSSで結果が異なる場合、Rに合わせません。採用する仕様を決め、差異を `docs/methods/` に記録します。比較のための調整（符号の反転、列の並べ替えなど）は検証側に書き、本番の結果を変えません。

## この文書の更新

基準では判断できない事例に出会ったら、実装より先にこの文書を更新します。実装した後で辻褄を合わせるために書き換えません。

変更したときは、既に書かれている `docs/methods/` の記述が新しい基準と矛盾しないかを確認します。
